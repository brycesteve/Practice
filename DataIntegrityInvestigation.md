# Training/body data integrity investigation

Code inspection and isolated unit tests only. No production store was opened for inspection or cleanup, no UI automation was run, and no diagnostic records were inserted into a live store. Consequently the exact IDs/origin of the user's three workouts cannot be certified from this investigation alone.

## Findings

1. **Unsafe schema promotion was a live-store writer.** `SettingsView` offered a DEBUG “Promote CloudKit Schema” button that passed the application's actual container to `CloudKitSchemaPromotionEngine.run`. The engine inserted every model's `makeSeed()` object, saved, and left cleanup commented out. Its relationship graphs included additional parent workouts. V2 seeds use nearly simultaneous start/end dates, morning workouts containing “Test”, 100 active calories and 100 average HR; these are diagnostic records, not genuine training. This is a concrete source of spurious history, independent of viewing/preparing a session. Invocation of this button has not been confirmed for the specific reported records.
2. **A second empty-workout path existed on Watch.** Ending an active workout saved a HealthKit workout and sent a `CompletedWorkout` even when no activity had been logged. Phone import accepted it. Finishing an evening workout incremented the counter unconditionally. Repeated asynchronous finish calls were also unguarded. Viewing/selecting a plan alone does not save a workout; Start begins HealthKit collection, and End & Save or completing/skipping through the plan calls finish. Cancel on the existing confirmation dialog simply cancels that dialog; it does not complete a workout.
3. **Readiness is not calculated from Practice workout records.** `RecoveryEngine` reads HealthKit HRV, resting HR, sleep, respiratory rate and active-energy totals/baselines. It does not consume workout count, last-trained date or elapsed recovery time from SwiftData history. Empty Practice workouts therefore cannot directly reset its calculation. However, `RecoveryScoreRecord.makeSeed()` hard-coded overall 100 with component scores 18/20/10/10/20/30; those components produce 17 under the actual weighting. Recent caches were trusted and could suppress recomputation; duplicate seeds could also be chosen for Watch sync. The body UI refactor did not change the readiness equation. With legitimately sparse HealthKit inputs the established model can still return 100; this investigation deliberately does not replace that model.
4. **Zero waist came from an explicit seed, not an optional-to-zero conversion.** The V3 waist `makeSeed()` added for the scale integration constructed `WaistMeasurementRecord(circumferenceCm: 0)`. Combined with the unsafe promotion action, this persisted zero centimetres with the current timestamp. Manual entry already checked 20–300 cm, HealthKit reads already required finite positive values, and body completion/Watch import never creates a separate waist record. The constructor previously had no validation. Profile resolution could select a newer zero seed over a genuine earlier waist. Adding the zero-waist seed to that unsafe path was a defect in the body-measurement implementation.
5. **Evening rotation was independent mutable state.** The dashboard and Watch used `eveningRotationDay`, not the last completed skill. Watch incremented it for every ended evening session, even empty ones, using its local settings snapshot. Phone accepted separate untimestamped rotation messages; schema promotion also added default AppSettings rows, while consumers selected an unordered `.first`. These mechanisms can leave a stale/reset counter, including a repeated Ring Skills suggestion. No migration reset was found: V3 keeps V2 model identities and existing settings. The particular message/order/row that produced the reported repeat cannot be established without reading the actual records.
6. **Sample screens were isolated, but test-host startup needed stronger isolation.** Body Stats sample data uses a separate in-memory, CloudKit-disabled container, never creates workouts/readiness, and bypasses normal launch services. Existing unit fixtures likewise use memory/temporary stores. However, the hosted app's normal startup previously had no general test guard; this is now explicitly isolated before constructing the app container or activating services.

## Fixes

- Removed the schema-promotion button. Its engine now throws before any insert/save, preventing accidental reuse against a live container. Existing seed methods in frozen schemas are retained only as historical code/test fixtures. Schema development must use a deliberately separate development store/account, not the app's real container.
- A shared completion predicate requires positive logged reps or timed activity and a valid interval; incidental calories, heart rate and elapsed time are insufficient. Real partial workouts remain valid. Empty Watch sessions are discarded without a HealthKit workout or phone transfer; duplicate finish execution is guarded. Phone import independently rejects empty/diagnostic workouts and deduplicates IDs in a dedicated context.
- Training summaries/consistency exclude empty records and the exact legacy workout-seed signature. History keeps them visible with a “not counted as training” explanation and its existing user-driven deletion action.
- Readiness weighting is unchanged and centrally reused to validate cached component/overall consistency. Inconsistent/future caches are not displayed, selected for upsert, or sent to Watch. The invalid rows are not deleted or overwritten; normal recomputation can create/use a valid cache instead.
- Waist construction and the store insertion boundary reject non-positive/non-finite values. Removed the zero-valued waist seed. Profile selection, charts and export skip existing invalid values without deleting them. Missing waist remains absent, and a body import cannot manufacture a waist entry.
- Automatic rotation derives from the most recent genuine completed evening skill exercise or legacy completed skill entry. It matches saved exercise names to progression levels/routines, rather than guessing from a counter. Ring Skills advances to Handstand in the existing ordering. Warm-up-only and empty sessions do not advance it. The numeric field remains a backwards-compatible fallback only when no completed-skill evidence exists.
- Added a small Watch evening-skill picker before preparing the workout. Selection changes only that plan. Completing a manually selected skill advances from that actual skill.
- Phone sync includes an optional completed-skill evidence projection; an offline Watch retains newer local completion evidence until the phone catches up. Old payloads still decode. Untimestamped legacy counter messages no longer overwrite authoritative history.
- Both unit-test schemes explicitly set `PracticeIsolatedTests=1`; iOS test hosts use a memory-only container, and both hosts skip normal UI/startup services. Tests assert that the isolation environment flag is present.

## Focused validation

- iOS: 30 relevant tests passed, covering the new integrity/persistence suites plus affected waist, migration, sync compatibility and readiness presentation tests.
- watchOS: 9 new integrity tests passed.
- The isolation test was additionally rerun once on each platform after adding an explicit environment-flag assertion; both passed.
- Both iOS and Watch app schemes build successfully. `git diff --check` passes.
- No broad UI/simulator inspection, no real-store seeding, no automatic cleanup.

## Existing records / manual cleanup

- **0 cm waist records are invalid observations.** They can be removed in a deliberate manual repair; they are now ignored and do not need deleting for correct current calculations. There is no existing waist-delete UI, so this change does not silently invent/run a cleanup operation.
- **Workouts confirmed to contain no completed activity**, after CloudKit relationships have finished syncing, and **recognisable diagnostic “Test” workouts** can be removed through the existing History deletion action. Review before deleting; a genuinely completed partial workout should remain.
- A **100 readiness row with exactly the seed's component/metric signature** is diagnostic and is now ignored. Do not delete genuine 100 scores merely because their overall value is 100.
- The old promotion action also seeded settings, progressions, skill sets, kettlebell records, rest days and conditioning/body records. If it was used, those related records merit manual review. Do not blanket-delete duplicate settings: inspect which row contains the intended preferences.
- Specific record IDs and the exact count of promotion invocations remain unverified; no claim is made that every suspect record has been individually identified.
